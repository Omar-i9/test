# محرك الخطط التكتيكية TAAMEN — Schema v1

**نطاق التنفيذ:** V14 Tactical Plan Engine Patch فوق مصدر V13 المستقر  
**الحالة:** نواة البيانات والتحويل والاسترجاع مطبّقة محلياً؛ المكتبة السحابية والحسابات مؤجّلة لمراحل لاحقة.

## 1. لماذا بدأنا من محرك البيانات؟

محرر الملعب هو المصدر الفعلي للخطة. يجب أن يستطيع المحرر حفظ الحالة نفسها التي يراها المستخدم، ثم استعادتها دون اختلاف، وبعدها يمكن لخدمة المزامنة والذكاء الاصطناعي قراءة البنية نفسها بدلاً من بناء صيغ مستقلة لكل ميزة.

كان في محرر V13 نظامان للإحداثيات:

- اللاعبون: نسب مئوية من 0 إلى 100.
- الرسومات: وحدات SVG ثابتة على ملعب أبعاده 900 × 540.

لو خزّنا القيم كما هي، سيبقى كل مستهلك جديد مضطراً لفهم نظامين مختلفين. لذلك أصبحت صيغة التخزين والتصدير الموحدة تستخدم إحداثيات نسبية من 0 إلى 1 لكل العناصر، بينما يحوّل المحرك القيم عند الدخول والخروج من المحرر.

## 2. ما الذي تمثّله Schema v1؟

الوثيقة القياسية تحتوي على:

- `format`: معرف ثابت للصيغة `taamen-tactical-plan`.
- `schemaVersion`: رقم إصدار بنية البيانات، وقيمته الحالية `1`. هذا مستقل عن تسمية إصدار الموقع V14.
- `id`: معرف الخطة.
- `metadata`: الاسم، الملاحظات، نوع اللعب، التشكيلة، تاريخ الإنشاء وآخر تحديث.
- `pitch`: نظام الإحداثيات وأبعاد الملعب المنطقية واتجاه العرض.
- `players`: كل لاعب، الفريق، رقم القميص، الاسم، وموقعه النسبي.
- `drawings`: كل رسم، نوع الأداة، نقطتا البداية والنهاية، والهندسة الكاملة عند وجود نقاط وسيطة.
- `styleToken`: رمز تصميم آمن ومحدد مسبقاً لكل أداة؛ لا نقبل CSS أو SVG خاماً من ملف مستورد.
- `layerOrder`: ترتيب الطبقات الحالي: الرسومات أولاً ثم اللاعبين.

### حدود النموذج الحالي

لم نضف خصائص غير موجودة في محرر V13 على أنها مدعومة. اتجاه الهجوم يبقى `unspecified` لأن الواجهة الحالية لا تتيح للمستخدم ضبطه. ولا نحفظ دور اللاعب كحقل مستقل لأن بطاقة المركز الحالية تستنتجه من موقع اللاعب. كذلك لا توجد ملاحظات نصية مثبتة على الملعب أو طبقات رسم مستقلة متعددة في المحرر الحالي.

## 3. الإحداثيات والتحويل

### داخل المحرر

- اللاعب `x/y`: نسبة مئوية من 0 إلى 100.
- الرسم `x/y`: إحداثيات SVG من 0 إلى 900 أفقياً ومن 0 إلى 540 عمودياً.

### في المستند الموحد

كل نقطة تستخدم:

```json
{ "x": 0.5, "y": 0.5 }
```

والتحويل عند الحفظ:

- اللاعب: `x / 100`, `y / 100`.
- الرسم: `x / 900`, `y / 540`.

والاسترجاع يعكس العملية. بهذه الطريقة لا تعتمد الخطة على حجم شاشة الهاتف أو الكمبيوتر.

## 4. الرسومات التي نحفظها

| أداة V13 | نوع البيانات | ما يتم حفظه |
|---|---|---|
| Pass | خط مستقيم | البداية والنهاية |
| Run | خط مستقيم | البداية والنهاية |
| Press | خط مستقيم | البداية والنهاية |
| Curve | منحنى تربيعي | البداية ونقطة التحكم والنهاية |
| Multi-curve | مسار متعدد النقاط | كل النقاط التي يعتمد عليها المسار |
| Zone | مستطيل منطقة | زاويتان تحددان المستطيل |

ترتيب الرسومات داخل المصفوفة محفوظ، وهو ترتيب الرسم الحالي. تُرسم طبقة الرسومات أسفل اللاعبين كما في V13.

### رموز الأسلوب

يُحفظ رمز ثابت لكل أداة، ولا يُستقبل كود تنسيق حر:

- `pass-solid-white`
- `run-dash-yellow`
- `press-dot-pink`
- `curve-solid-violet`
- `multi-curve-dash-cyan`
- `zone-fill-amber`

في هذه المرحلة، الرمز يصف هوية الأداة المرئية الحالية. لم نضف أداة تخصيص ألوان منفصلة أو نظام طبقات قابل لإعادة الترتيب.

## 5. واجهة المحرك البرمجية

الملف الأساسي:

`src/domain/tactics/tacticalPlanSchema.ts`

الدوال الرئيسية:

- `serializeTacticalPlan(state)`: يتحقق من حالة المحرر ثم يحولها إلى Schema v1.
- `parseTacticalPlan(value)`: يتحقق من مستند v1 أو يقرأ سجل V13 القديم ويحوّله في الذاكرة.
- `parseTacticalPlanJson(json)`: يفحص حجم النص ثم يحلّل JSON ويتحقق منه.
- `restoreTacticalPlan(value)`: يعيد بيانات Schema v1 إلى وحدات المحرر الحالية.
- `isTacticalPlanDocument(value)`: يتحقق من أن القيمة مستند v1 صالح.

الأنواع الأساسية:

- `TacticalPlanDocument`
- `TacticalPlanPlayer`
- `TacticalPlanDrawing`
- `TacticalBoardState`

## 6. التحقق والحماية

يتم رفض المستند إذا خالف أي قاعدة جوهرية، ومنها:

- نوع لعب غير معروف أو تشكيلة غير مدعومة.
- عدد لاعبين لا يطابق 5 أو 7 لاعبين لكل فريق.
- أرقام قمصان غير صحيحة أو مكررة داخل الفريق نفسه.
- معرفات مكررة.
- إحداثيات خارج المجال النسبي 0–1.
- نوع رسم أو رمز أسلوب غير معتمد.
- منحنى لا يحتوي ثلاث نقاط، أو مسار متعدد الانحناءات لا يحتوي نقطتين على الأقل.
- أكثر من 250 رسماً، أو أكثر من 800 نقطة للرسم، أو أكثر من 50,000 نقطة إجمالاً.
- ملف JSON أكبر من 2 MiB.
- مفاتيح خطرة مثل `__proto__` و`constructor` و`prototype`.
- إصدار مستقبلي غير معروف.

لا يُقبل إدخال CSS أو HTML أو SVG خام داخل بيانات الخطة.

## 7. التوافق مع بيانات V13 وترحيلها

V13 كانت تستخدم مفاتيح IndexedDB التالية:

- `plan-v3-5v5`
- `plan-v3-7v7`
- المفتاح المشترك السابق `plan-v3`
- المفتاح التاريخي الأقدم `plan`

لم نغيّر اسم قاعدة البيانات أو إصدارها أو مخزن `tactical`. لا يوجد IndexedDB migration جديد ولا حذف تلقائي للمفاتيح القديمة.

عند القراءة:

1. يقرأ المحرك السجل الحالي.
2. إذا كان مستند Schema v1 صالحاً، يستعمله مباشرة.
3. إذا كان سجل V13 القديم صالحاً، يحوّله إلى v1 ثم يحفظ النسخة القياسية في المفتاح نفسه.
4. يظل مفتاح `plan-v3` المشترك والمفتاح الأقدم محفوظين بعد النسخ.
5. إذا كان سجل قديم غير صالح أو غير قابل للقراءة، تؤخذ منه نسخة داخل مخزن `metadata` بالمعرف `tactical-plan-recovery-v1:<sourceId>` قبل السماح بإنشاء سجل جديد مكان المفتاح النشط.
6. إذا تعذر حفظ نسخة الاسترداد بسبب امتلاء التخزين أو فشل IndexedDB، يمنع المحرك الكتابة فوق ذلك النمط في الجلسة الحالية.

نسخة الاسترداد سجل محلي احتياطي وليست واجهة استعادة للمستخدم بعد. ينبغي تطوير شاشة استعادة واضحة لها قبل إطلاق تغييرات واسعة على دورة حياة البيانات.

## 8. السلوك الحالي بعد التنفيذ

للحفاظ على توافق V13، يستمر المحرر حالياً بالحفظ التلقائي المحلي في مفتاح مستقل لكل نمط لعب، مع أزرار التصدير والاستيراد الحالية. استيراد ملف إلى نمط يحتوي خطة محفوظة يعرض تأكيداً قبل الاستبدال.

**هذا ليس تنفيذ مكتبة الخطط السحابية بعد.** لم تُنشأ حسابات أو D1 أو مزامنة. كما لم نغيّر بعد قاعدة المنتج المستقبلية التي تفصل مسودة الاسترداد المحلية عن مكتبة الخطط الدائمة التي ستكون للحساب السحابي. سيتم تنفيذ ذلك عندما نصل إلى طبقة الصلاحيات والحسابات، بعد تأمين تجربة المحرك.

## 10. ما لم يتم تنفيذه في هذه المرحلة

- لا حسابات ولا بريد إلكتروني ولا جلسات سحابية.
- لا D1 ولا ترحيلات Cloudflare.
- لا مزامنة بين الأجهزة.
- لا مكتبة خمس خطط سحابية لكل صيغة بعد.
- لا إرسال الخطة إلى TAAMEN AI حتى الآن.
- لا تغيير في AI Worker أو حد الاستخدام.
- لا تغيير في تصميم الملعب وأدواته أو الألوان أو الحركة.
- لا تغيير في `package.json` أو `package-lock.json` أو إعدادات Wrangler.

هذه الحدود مقصودة لتقليل مساحة التغيير وتسهيل مراجعة المحرك قبل بناء الطبقات المعتمدة عليه.
